Branch-scoped development data

Repobox gives every local Git branch persistent remote PostgreSQL data while application processes remain local. The first implementation uses PlanetScale and Docker Compose through a terminal-only Rust CLI that is equally operable by humans and agents.

Decision required: Confirm that v0.1 should ship the local control-plane architecture, PlanetScale-only PostgreSQL provider, forward-only pull semantics, and versioned agent CLI contract before the first tagged release.

Summary

repobox run loads or detects a repository, provisions isolated remote PostgreSQL data for the Git environment, injects credentials into local processes, and presents logs in a fast terminal UI. Provider mutations are checkpointed, while automation receives versioned JSON or JSONL.

Decision required

Confirm the v0.1 boundaries above. Hosted compute, additional providers, masking hooks, and periodic source resync remain later work.

Problem and user need

Databases consume local disk and memory, are slow to reconstruct, and are commonly shared accidentally across branches. Repositories also lack a standard, secret-safe way to tell humans and agents how to acquire the correct durable development data.

Current behavior

Each repository invents its own Compose lifecycle, environment-file convention, and database copy scripts. Branches usually share mutable data, secrets leak into local files, and failed provider work has no durable recovery handle.

Proposed behavior

  1. Detect every Compose PostgreSQL service and create strict project configuration plus managed agent-guide blocks.
  2. Map the selected Git environment, including main, to deterministic PlanetScale branches.
  3. Store one-time role credentials outside the repository and inject URLs only into child-process environments.
  4. Remove remote database services from an in-memory Compose model and pass transient YAML over stdin.
  5. Stage and checkpoint forward-only refreshes so partial failures can resume without guessing.
  6. Require confirmation for destructive or billable work and expose dry-run, JSON, and JSONL forms.

API and data model changes

repobox agent-context --schemas --json

success:  { schema_version, command, data }
mutation: { ...resource, undo_command, undo_reason }
stream:   { schema_version, sequence, timestamp, event, data }
error:    { schema_version, error: { kind, code, message, ... } }

The project input is a strict version-1 .repobox.yml. Unknown keys fail validation, while secrets remain outside both project configuration and durable state.

Architecture diagrams

Inside Repobox, the CLI coordinates core state, the environment manager, the provider adapter, the Compose adapter, the credential store, and the event-driven TUI. Provider and runtime traits are the seam for later E2B or Modal execution.

Alternatives considered

  1. Go — faster compiles, but Rust better fits one safe low-overhead binary and explicit state machines.
  2. Local-only Compose — does not deliver persistent isolated data.
  3. Always-on daemon — adds lifecycle and security complexity too early.
  4. Edit Compose or .env — leaks secrets and takes ownership of user files.
  5. Terraform UX — mismatched to a fast branch-by-branch loop and log surface.

Credential leakageHighLowNo secret flags/files; keyring, process env, redaction, tests.

Rollout and migration plan

  1. Land implementation, schemas, docs, and CI without a tag.
  2. Verify offline on Linux and macOS.
  3. Run the credentialed provider smoke and clean every resource.
  4. Tag v0.1.0 and publish checksummed, attested artifacts, crates, and Homebrew formula.

Rollback plan

Before release, revert the bootstrap. After release, deprecate the affected release and publish a patch. Remote environments are only deleted by an explicit repobox env delete NAME --yes. Interrupted pulls resume forward; deleted old branch data has no rollback.

Test plan

  • Unit tests for config, identity, state, jobs, redaction, guides, Compose, and TUI coalescing.
  • Provider wire tests for authentication, pagination, and permission errors.
  • Black-box tests for help, structured errors, detection/init, dry-run, and schemas.
  • Release-gating live smoke for create, rerun, run, pull, interruption, degraded state, delete, and cleanup.

Observability and operations

Atomic project state and append-only jobs record bindings, steps, failures, and timestamps. Status, service status, job view, and doctor commands expose that state; request IDs appear on provider failures. v0.1 sends no telemetry events.

Security and privacy review

Tokens are entered through a hidden prompt or environment variable and never accepted as secret flags. Role URLs stay in the OS credential store or a permission-restricted explicit fallback. Local import is opt-in, streams without a dump file, and performs no masking, so users remain responsible for source-data classification.

Open questions

None — v0.1 choices were resolved before implementation. Hosted compute and periodic resync are later-version work.

Appendix: terminal rendering

The TUI applies reducer-owned state, dirty/coalesced presentation, one frame in flight, synchronized updates, dedicated buffered output, dedicated input, and a paint cap without an always-running timer. It uses upstream Ratatui and does not copy Grok Build's inline-terminal fork.
